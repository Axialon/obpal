ob.Pal field guide

A clear first phone-control demo.

Prepare one browser task. Show the input and the response. Find out whether a handheld controller helps.

Allow about ten minutes for the exercise, plus setup and troubleshooting. This is a planning budget, not a measured setup guarantee.

Choose the task before the technology.

Pick one object or control in the approved browser example. Describe a clear finish: “Move this object to the marked position,” or another task the current build supports. Say why handheld input might help while the display stays visible. Avoid beginning with a QR code or a list of features.

Prepare a clean entry.

  1. Use a host screen with an internet connection and the approved browser example. Use a real phone with its browser. Write down both browser versions, the phone model, the date and the example build.
  2. Start from a fresh page on both devices. Follow the example's own host entry and phone pairing prompts. Explain the QR or typed-code route after the participant understands the task.
  3. Check that the connection indication appears on the correct devices. Use the native comparison guidance; the seal is not a certificate or permission to control a PC.
  4. If the selected control needs motion permission, let the participant choose. If they decline or it is unavailable, use the supported touch route for an appropriate task. Do not imply the touch and motion tasks are identical.
  5. Keep private tabs, notifications and personal information out of the display. Do not ask for an account or email just to observe the trial.

Use this short script.

“This experience stays on the main display. Your phone will hold the controls. The task is to [name the supported task and finish]. First I'll show what changes, then we'll connect your phone. You can stop at any time.”

“Use the control once. What changed on the display? Try the same task using the input you normally use. Which would you choose here, and why?”

“What would prevent you from trying this in something you're building?”

Record the useful moment.

With permission, note whether the participant could explain the benefit, begin without help and finish the named task. Count the attempt even if it fails. Note assistance, permission denial, wrong entry or recovery. If timing is relevant, measure from the agreed entry action to the first intended response; do not call it network latency.

Your trial card

  • Task and clear finish.
  • Date, build, phone/browser and host/browser.
  • Normal input and what it does well.
  • First intended response reached? Help needed?
  • Failure and recovery, if any.
  • Phone helped because / made harder because.
  • Participant's next useful question.
  • Keep, change or test next.

Keep notes privately. Permission to try is separate from recording, quoting or email updates. This page does not collect trial notes.

If it breaks, keep the explanation honest.

Stop the attempt and describe the failed step. Follow the native disconnect/reconnect guidance. If recovery fails, end the task and record it. A labelled recording can show a previous run; say that it is recorded and name its conditions. A scripted diagram can explain the concept, but cannot replace real-phone proof.

Build from the result.

If the handheld benefit is clear, inspect the ob.Pal source and protocol for your browser experience. Check the actual component licence and excluded brand/demo assets. Keep Link/extension/native PC routes as separate integration work.
