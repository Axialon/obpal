Browser Input Readiness Review

One browser task with phone input.

Decision: test first. A handheld touch controller is a source-supported candidate for moving one browser-scene object while the participant faces a separate display.

The SDK exposes scene ownership, frame deltas and join/leave events. The remaining decision depends on the actual fresh-entry task and comparison with the existing input. Source review does not prove this sample task's physical-phone flow.

The bounded brief.

  • Experience: an existing browser scene with one selectable object and a marked destination.
  • Task: move the object to the destination, then reset it once.
  • Benefit hypothesis: controls stay in the participant's hand while the display stays visible to them and others.
  • Baseline: the scene's existing keyboard/mouse input. Keep it available; no superiority claim.
  • Candidate: one phone, face.trackpad, touch input first. Sensor-based controls and native PC permissions are separate work.
  • Finish: the object reaches the agreed target and the participant deliberately resets it.

Integration sketch, not an executed patch.

  1. Explain the destination task beside the scene before exposing pairing.
  2. Define the native element once; choose one seat and the documented trackpad face.
  3. Publish one named scene node. Assign a joining participant only if holder('cube') says that node is free.
  4. In the existing render loop, consume that participant's frame only while they hold the node. Map pad1 into the scene's coordinate system and clamp movement to the task area.
  5. Keep the existing reset function and normal input route. Connect the tray event to reset without adding unrelated permissions.
  6. On leave or rejected/failed entry, keep the existing input usable, explain the state and let the person choose a supported retry.
  7. Follow native lifecycle, teardown, brand geometry and CSP guidance.

No code is installed or executed by this sketch. This preview creates no room or connection. An implementation contract would separately define the actual scene/API surface and testing.

Trial and stop card.

Use the field guide. Begin with a fresh host and real phone page. Explain the task, compare correct-device indications, then ask for one move and one reset. Compare with the baseline. With permission, note build/devices, finish, help, blocked step and recovery. Keep private tabs and personal data out of the record. An entry-time observation is not network latency.

Stop at a blocked essential step or ambiguous control authority; retain the baseline input. Label a recording as recorded. An illustration is explanatory only. Recommend integration only after the intended task can be repeated and a practical handheld benefit is identified. A negative result is a valid review outcome.

An actionable handoff.

Name the one scene, input baseline and candidate device combination. Run the fresh task using the native route. Then choose a separately scoped implementation patch or keep the current input. This sample shows a complete readiness-review structure; it does not certify a device run or promise compatibility.
