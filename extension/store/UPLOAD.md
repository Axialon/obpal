# Keeping the Link store update current

The owner submits the existing item by hand in the [Developer Dashboard](https://chrome.google.com/webstore/devconsole). These commands prepare files and record dashboard actions; they never upload anything.

1. Run `pnpm run store -- status`. It shows published, pending and prepared versions, each field and image compared with the last submission, zip freshness, and whether GitHub is ahead. Run `pnpm run store:art` when art inputs changed (with the coordinator's assigned capture ports), then `pnpm run store:extension`. A full art render updates `art.json`; partial renders and `--out` previews do not certify the complete set. Commit the source, listing and art before recording a submission.
2. Run `pnpm run store -- kit` (`store:kit` remains an alias), or `pnpm run store -- serve 5186` from the durable main checkout. A validated new kit updates the tracked prepared version; commit that change before recording submission. The server binds loopback, regenerates on every page request, disables caching and stops with Ctrl+C. Open its printed URL. Do not copy the HTML to a review folder: keep the kit and its relative image references in the checkout. A failed regeneration removes the previous kit and explains how to rebuild.
3. Follow the kit's numbered dashboard steps for the existing item. Use **Copy path** for file dialogs, or **Download** from the live server to retrieve any upload file. Replace the CHANGED fields and images, and save drafts on each edited tab. The header shows the item ID, comparison and generation time. The kit checks live destinations for HTTP 200 and checks version, browsers, modes, Windows PC and every permission justification. Release-description changes compare with the published ledger version; field and image markers compare with the last submission. Absolute paths exist only in the ignored generated kit. File links work over HTTP while serving; a static kit opened locally uses the same relative upload paths. Explorer actions are omitted.
4. After the owner confirms submission in the dashboard, run `pnpm run store -- submitted <version>`, then commit `extension/store/submissions.json` and `status.json`. This requires committed tracked inputs and a current store zip. The ledger records the source commit, submission date, zip hash, field hashes and image hashes. Version 1.8.0 starts prepared, awaiting this confirmation.
5. Record the dashboard outcome with `pnpm run store -- published <version>` or `pnpm run store -- rejected <version> "<generic reason>"`, then commit the ledger and status. Reasons describe the review issue only: never include names, emails, account details, links or local paths. A rejected version may be resubmitted after fixes are committed. The comparison baseline remains the last submission, including rejected submissions. Run `pnpm run store -- check` or `pnpm run check` to catch contradictions.

The historical 1.6.2 entry uses its source commit and original listing/image hashes. Its original submitted zip and submission date are unavailable: the ledger explicitly records a null zip hash and a commit-date proxy, and records publication as observed on the migration date. Existing 1.8.0 art is adopted as the initial art receipt; subsequent full renders refresh it.

A missing zip or missing receipt on a fresh checkout is expected: `pnpm run store:extension` builds both. Matching version numbers alone do not prove freshness. Build receipts include tracked and untracked extension inputs and shared dependencies; packing rejects altered build output. Store submission requires a clean tracked tree so recorded content is recoverable from its commit.

`ship` and `check:live` warn when the published store version lags GitHub. Pending review still counts as lagging until published. This warning does not fail a release check.
